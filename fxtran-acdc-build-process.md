# IAL GPU build with fxtran-acdc

> [!info] Context
> Build observed live in `/tmp/IAL-build/build.GPUCC80_O1_NVHPC26.5_CUDA12.9_HPCX2.25.1`
> (IAL = IFS/Arpège limited-area model, `ial_dp` = double precision).
> Toolchain: NVHPC 26.5, CUDA 12.9, HPC-X 2.25.1, target `cc80` (A100), `-O1`.
> Sources: `/tmp/IAL-build/source/fxtran-acdc` (author: philippe.marguinaud@meteo.fr, Météo-France).
>
> *Note: this build tree was cleaned out after the session; the paths below are kept as concrete examples — the process described is generic to any `FXTRAN_*` build.*

**ACDC** = *Adaptation des Codes à Divers Calculateurs* ("adapting codes to various computers"). It is a source-to-source translation framework: Fortran is parsed to XML by `fxtran`, transformed by Perl modules (`Fxtran::*`), and emitted back as Fortran with OpenACC/OpenMP pragmas. The whole machinery is injected into a normal CMake/ecbuild build **by replacing the compilers with wrapper scripts**.

---

## 1. Big picture

```
ecbundle-build --arch bundle/arch/fxtran/ --build-type FXTRAN_GPUCC80_O1_NVHPC26.5_CUDA12.9_HPCX2.25.1
        │
        ▼
configure.sh ──► env.sh (modules, PATH, PERL5LIB, toolchain.cmake.pl)
        │            └──► toolchain.cmake:  CMAKE_Fortran_COMPILER = arch/fxtran/f90   ← wrapper!
        │                                   CMAKE_C/CXX_COMPILER   = arch/fxtran/cc|cxx
        │                                   CMAKE_AR               = arch/fxtran/ar
        ▼
build.sh ──► make -j32
        │      └── sub-makes go through arch/fxtran/make (fxtran-make)
        ▼
for each file.F90:  arch/fxtran/f90  ──►  fxtran-fix ──► fxtran-f90 ──► pgf90
                                              │              │
                                              │              ├─ scan source for "!$ACDC <method>" directives
                                              │              ├─ per directive: fxtran-gen Fxtran::Generate <method>
                                              │              │      → .fxtran/generated/<name>_<variant>.F90
                                              │              ├─ inner "make -j16" compiles all variants in parallel
                                              │              └─ ar crv file.F90.o  O_name.o O_name_openacc.o ...
                                              │
                                              └─ on failure: open xterm debug shell (aliases r / e)
```

---

## 2. Bootstrapping: how the wrappers get in

### `configure.sh` / `build.sh`
Generated by **ecbundle 2.4.0**. `build.sh` sources `env.sh`, then runs plain `make -j32 VERBOSE=1`, teeing to `build.log`.

### `env.sh` (arch/fxtran/env.sh)
- purges/loads site modules (NVHPC, CUDA, HPC-X, netcdf, hdf5…),
- exports `FP_PRECISION=double` (hence `ial_dp`, `-r8`),
- symlinks `source/fxtran-acdc` → `$BUILD/fxtran-acdc` and prepends its `bin/` to `PATH`, `lib/` to `PERL5LIB` (all `fxtran-*` tools are Perl scripts using `Fxtran::*` modules),
- runs `toolchain.cmake.pl $BUILD_TYPE …` to generate `toolchain.cmake`.

### `toolchain.cmake.pl`
Parses the build-type string with a regex:

```
FXTRAN_(GPU\w+|CPU)_O([0-3])_NVHPC([\d.]+)_CUDA([\d.]+)_HPCX([\d.]+)
```

and writes `toolchain.cmake` setting **the wrappers as the actual compilers**:

```cmake
set (CMAKE_Fortran_COMPILER  "<arch>/f90")
set (CMAKE_C_COMPILER        "<arch>/cc")
set (CMAKE_CXX_COMPILER      "<arch>/cxx")
set (CMAKE_AR                "<arch>/ar")
set (OpenACC_Fortran_FLAGS   "-cuda -acc=gpu -gpu=cc80 -Minfo=accel,all,ccff
                              -DFXTRAN_ACDC_VENDOR=FXTRAN_ACDC_NVIDIA
                              -DFXTRAN_ACDC_PRAGMA=FXTRAN_ACDC_OPENACC")
set (ECBUILD_Fortran_FLAGS   "-fpic -Mframe -Mbyteswapio -Mrecursive -Kieee -Mdaz
                              -Mbackslash -Mlarge_arrays -Mstack_arrays -traceback")
```

> [!note] Key insight
> CMake/ecbuild never calls `pgf90` directly. Every compile, archive and link line in the generated Makefiles invokes a wrapper from `bundle/arch/fxtran/`. That is how pre-processing is triggered transparently per file, with zero changes to the project's CMakeLists.

## 3. The wrapper scripts (`bundle/arch/fxtran/`)

| wrapper | expansion | role |
|---|---|---|
| `f90` | `fxtran-fix --type xterm -- fxtran-f90 --pragma $FXTRAN_PRAGMA --prefix $BUILD/.fxtran/acdc --config fxtran.conf -- $FXTRAN_F90 $*` | Fortran "compiler": ACDC pre-processing + real compile |
| `cc` / `cxx` | `fxtran-fix … -- fxtran-cc --prefix …/.fxtran/acdc --config fxtran.conf -- $FXTRAN_CC $*` | C/C++ compile/link; injects `-lFxtranACDC` runtime + includes at link |
| `ar` | `fxtran-fix … -- fxtran-ar -- $FXTRAN_AR $*` | archive tool that understands **nested archives** (see §6) |
| `make` | `fxtran-make --config fxtran.conf -- /usr/bin/make $*` | syncs user-edited generated sources before building (see §7) |
| `fxtran.conf` | default generation options | see below |

### `fxtran.conf` — global generation defaults
```perl
[ '--create-interface', '--cycle' => '50', '--gpumemstat',
  '--inline-contained', '--merge-interfaces',
  '--methods-list' => 'crc64,size,host,copy,wipe,save,load,update',
  '--post-parallel' => 'synchost,nullify',
  '--process-interfaces', '--stack84',
  '--types-constant-dir'  => "$BUILD/.fxtran/types-constant",
  '--types-fieldapi-dir'  => "$BUILD/.fxtran/types-fieldapi",
  '--user-directory-out'  => "$BUILD/.fxtran/generated",
  '--user-directory-in'   => "$BUILD/.fxtran/user-in",
  '--user-directory-directives' => "$BUILD/fxtran-directives",
  '--use-acpy', '--split-util', '--parallelmethod-section',
  '--object-merge-method' => 'archive', '--write-metadata' ]
```

## 4. `fxtran-f90` — the heart of the pre-processing

Perl compiler wrapper (`bin/fxtran-f90`). For each Fortran file:

1. **Splits argv at `--`**: left = fxtran generation options, right = the real `pgf90 …` command.
2. **Reads the source and greps for `!$ACDC` directives.** Example from `arpifs/phys_ec/cuascn.F90`:
   ```fortran
   !$ACDC singlecolumn --inlined cuadjtq.F90,cubasmcn.F90,cuentr.F90,cuadjtqs.F90
   !$ACDC manyblocks --max-statements-per-parallel=20 --inlined cuadjtq.F90,...
   ```
   (A per-file override can also live in `$BUILD/fxtran-directives/` — `--user-directory-directives`.)
3. **For each directive**, spawns (`runACDCMethod`):
   ```
   fxtran-gen Fxtran::Generate <method> <config opts> <directive opts> -I… file.F90
   ```
   in a temp dir. Output lands in `.fxtran/generated/`:
   - `cuascn.F90` — plain reference source,
   - `cuascn_openacc.F90` — `CUASCN_OPENACC`, marked `!$ACC ROUTINE … SEQ`,
   - `cuascn_manyblocks.F90` — `CUASCN_MANYBLOCKS … LDACC, KGPBLKS` driver with `!$acc loop gang` / `!$acc loop vector(klon)`,
   - `*.intfb.h` — interface blocks (`--create-interface --merge-interfaces`).
4. **Compiles all variants** (`Fxtran::F90Compiler::compile/make`): writes a small `Makefile` into the temp dir and runs an **inner `make -j16`**, adding ACDC runtime flags for generated variants:
   ```
   -L$BUILD/.fxtran/acdc/lib -lFxtranACDC -DFXTRAN_ACDC -DFXTRAN_FILE=__FILE__ -DFXTRAN_LINE=__LINE__
   ```
5. **Merges the variant objects into one**. With `--object-merge-method archive`:
   ```
   ar crv cuascn.F90.o  O_cuascn.o  O_cuascn_openacc.o  O_cuascn_manyblocks.o
   ```
   → the final "object file" presented to CMake is actually **an `ar` archive** (verified: `file cuascn.F90.o` ⇒ "current ar archive"). Alternative: `ld -r`.
6. Moves generated `.mod` files back into the module output dir.
7. Files **without** `!$ACDC` directives bypass generation and are compiled straight (`Fxtran::F90Compiler::run`).

## 5. Transformation methods (`Fxtran::Generate`, `lib/Fxtran/*.pm`)

| method | module | what it does |
|---|---|---|
| `singlecolumn` | `Fxtran::SingleColumn` | NPROMA-block vector routine → per-column `!$acc routine seq` kernel; threads of a warp each process one column; NPROMA temporaries scalarized / stack-allocated; `--inlined` pulls callee sources in |
| `manyblocks` | `Fxtran::ManyBlocks` | NPROMA routine → multi-block routine (extra block dim on all NPROMA args); host driver spawning OpenACC kernels (single-column kernels, may call `singlecolumn` routines); kernel splitting via `--max-statements-per-parallel` or explicit `!$ACDC PARALLEL` regions; constants & inputs assumed device-present on entry |
| `pointerparallel` | `Fxtran::Pointer::Parallel` | rewrites parallel-region pragmas into **runtime-dispatched IF/ELSEIF over backends** (OpenMP/OpenACC); rewrites Field-API array refs to host/device views, re-associates pointers; emits `SGET_HOST_DATA_{RDONLY,RDWR}`, `SYNCHOST`, `NULLIFY` sections (`--post-parallel synchost,nullify`) |
| others | | `singleblock`, `toplevel`, `toplevelsi/sp`, `spectral`, `semiimplicit`, `bitrepro`, `updateconstants`, `openaccconvert`, `interface`, `methods` (introspection), … |

Cross-file knowledge comes from metadata DBs: `.fxtran/types-constant` and `.fxtran/types-fieldapi` (per-cycle: `--cycle 50`), plus `Fxtran::Finder::*` to locate sources (incl. `Finder::CMake` which reads CMake target file lists).

## 6. Link side: `fxtran-ar`, `fxtran-cc` and the runtime

- Because "objects" can be archives of variant objects, **`fxtran-ar`** flattens them when building static libs (`ar q/qc`): extracts `O_*.o` members and re-archives. `libarpifs.DP.a` etc. are built this way.
- **`fxtran-cc`** adds the ACDC runtime include dir and `-lFxtranACDC` on link lines.
- **Runtime** (`source/fxtran-acdc/src`, installed to `.fxtran/acdc/`): `libFxtranACDC.a` + modules — device malloc, array copy (ACPY), bit-repro intrinsics (`crc64`), GEMM wrappers per variant, GPU mem statistics (`--gpumemstat`), `FXTRAN_ACDC_LSYNCHOST`, the stack allocator used by `--stack84`, etc. Generated code calls into it (`FXTRAN_ACDC_*` macros select vendor/pragma at compile time).

## 7. `fxtran-make` — user-editable generated code

> [!tip] Round-trip engineering
> Generated sources in `.fxtran/generated/` are **meant to be hackable**. Before delegating to `/usr/bin/make`, `fxtran-make`:
> - compares mtime of each file in `generated/` (user-out) against the metadata timestamp written at its end;
> - if the user edited it → copies it to `.fxtran/user-in/` and *touches the origin source* so CMake rebuilds it (generation then takes `user-in` as input instead of the repo source);
> - if a file was deleted from `generated/` → removed from `user-in`, back to normal pipeline.
>
> So you can hand-tune e.g. `lascaw_openacc.F90`, rebuild, and your edits survive regeneration.
> CMake's sub-makes are invoked through this wrapper (seen in `build.log`: `arch/fxtran/make -f ial_dp/CMakeFiles/arpifs.DP.dir/build.make …`).

## 8. `fxtran-fix` — error trapping (observed live)

Wraps every compiler invocation. Logic (`bin/fxtran-fix`):

```perl
goto END unless ($ENV{FXTRANFIX});       # pass-through if disabled
exit (0) unless (system (@cmd));         # run compile; exit if OK
# on failure: create tmpdir with run.sh / bashrc / shell.sh
system (qw (xterm … -e), $shell);        # interactive debug session
```

The xterm shell gets:
- `alias r = <tmpdir>/run.sh` — re-exec the exact failed command (`set -x; exec fxtran-f90 …`),
- `alias e = vi <source file>`,
- `run.sh` is executed **once automatically** by the bashrc,
- on shell exit, `fxtran-fix` retries the compile once more and returns status to `make`.

> [!important] This is a deliberate design, not an accident
> `FXTRANFIX` exists **on purpose**: instead of the classic painful loop —
> *make fails → hunt the error through megabytes of build.log → edit the source → re-run cmake/make* —
> the failing compile is frozen in place and the user is dropped into a shell **with the exact failing command and all generation artifacts at hand**. You inspect, fix, retry with `r`, and simply exit the shell; the suspended `make -j32` then resumes exactly where it stopped. The rest of the parallel build is preserved — nothing is re-done.
>
> The mechanism serves **two** purposes:
> 1. **Fixing the model Fortran source code** — correct the `!$ACDC` directives or the Fortran of the file being compiled, rerun with `r`, done.
> 2. **Developing the fxtran-acdc toolkit itself** — the debug shell hands the toolkit developer the *exact* failing `fxtran-gen` / `fxtran-f90` command line, together with the temp dirs holding the intermediate artifacts (parsed XML, partially transformed Fortran, per-variant outputs). One can then iterate live on the `Fxtran::*` Perl modules (e.g. `SingleColumn.pm`, `ManyBlocks.pm`, `Pointer/Parallel.pm`) — edit a transformation, hit `r`, inspect the freshly generated code — which makes FXTRANFIX the natural workbench for **developing new functionalities (methods, options) and fixing generator bugs**, not merely a compile-error recovery tool.

> [!example] The cuascn session (2026-07-28) — a controlled drill
> The `NVFORTRAN-S-0038 Symbol 'www' has not been explicitly declared` failure at line 2–3 of the generated `cuascn*` variants was **injected deliberately** to fire the FXTRANFIX mechanism and land in an xterm debug session. It worked exactly as designed:
> 1. 08:27 — compile fails, `fxtran-fix` traps it, opens the xterm (`r`/`e` aliases, `run.sh`);
> 2. the bashrc's automatic first `run.sh` re-executes the exact compile; with the injected fault removed, generation + compilation succeed and `cuascn.F90.o` (888 346 B, 3 members) is archived at 08:29;
> 3. the build stays parked only because the debug shell is still open — the user holds the control until deciding to hand it back to `make`;
> 4. re-running `r` by hand later reproduced a byte-identical object, confirming the pipeline itself is deterministic and healthy.

## 9. Where generated things live

```
$BUILD/
├── .fxtran/
│   ├── acdc/{include,lib}     # ACDC runtime prefix (fxtran-boot product)
│   ├── generated/             # user-directory-out: transformed sources (.F90, .intfb.h)
│   ├── user-in/               # user overrides fed back into generation
│   ├── types-constant/        # constant/type metadata DB
│   └── types-fieldapi/        # Field-API type metadata DB
├── fxtran-directives/         # per-file !$ACDC directive overrides
├── fxtran-acdc -> source/…    # symlink, tools on PATH/PERL5LIB
└── ial_dp/
    ├── *_type_mod.F90         # generated model type modules (cpg_*, field_*, surface_*…)
    ├── field_registry_mod.F90, variable_module.F90, autopromoted_files
    ├── generated_interfaces/  # 51 merged .intfb.h
    ├── module/                # 553 .mod (incl. fxtran_acdc_*_mod)
    └── arpifs/interfaces/     # FCM-generated interface blocks (fcm-make-interfaces.*.cfg)
```

## 10. Thoughts / assessment

> [!success] Elegant aspects
> - **Zero-intrusion injection**: replacing `CMAKE_Fortran_COMPILER` keeps all CMakeLists untouched; generation options centralised in one `fxtran.conf`.
> - **Directive-driven**: the `!$ACDC` comments live in the source, next to the code they transform; methods compose (`singlecolumn` kernels callable from `manyblocks` drivers).
> - **One object per source**: variant objects are hidden inside an archive, so CMake's dependency graph stays simple; `fxtran-ar` flattens at lib time.
> - **Developer ergonomics**: `fxtran-fix` replaces the tedious *make → grep the logs → edit → re-cmake* cycle with an interactive debugging session opened right at the failing compile, without killing the 32-way parallel build — serving both model developers (fixing Fortran) and toolkit developers (iterating live on the `Fxtran::*` transformation modules with the exact failing command and artifacts at hand); `fxtran-make` makes generated code a first-class editable artifact.
> - **Bit-repro / tooling**: `crc64` method list, `--gpumemstat`, `--write-metadata` show the framework doubles as a verification harness.

> [!warning] Points of attention (not flaws)
> - **The build waits for the human — by design**: with `FXTRANFIX` set, a failed file parks its make branch behind an xterm until the user exits the debug shell. That is the intended interactive workflow (fix in place, resume without rebuilding anything else), but it means one must remember to close the session; on headless/batch runs, leave `FXTRANFIX` unset so failures degrade to plain errors.
> - **Nested archives as "objects"**: clever, but any tool in the chain that assumes plain ELF objects (some linkers, `ld -r`, LTO, certain profilers) will trip; hence the need for `fxtran-ar` everywhere.
> - **Timestamp-based sync** in `fxtran-make` (mtime vs embedded metadata) can be fooled by NFS clock skew or `touch`.
> - **Error provenance**: failures surface deep in Perl (`Fxtran/Util.pm:121 system() and die`) with long `@cmd` dumps; root cause requires reading `r.eo`/`build.log` tails — though with FXTRANFIX active you are placed directly at the failing command instead.
